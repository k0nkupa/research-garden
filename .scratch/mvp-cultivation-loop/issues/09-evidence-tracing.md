# 09: Evidence tracing signature interaction

**What to build:** The interaction the product is for. A person selects a Claim Leaf or a Harvest and the Tree softens everything unrelated while illuminating the complete path from its Roots through its supporting items to the selection. Disagreement looks different from support. Provenance becomes something they can see rather than something they have to reconstruct, and the panel opens the content at the same moment so structure and substance are legible together.

**Blocked by:** 08

**Status:** resolved

- [x] Selecting an item softens unrelated regions of the Tree and illuminates its complete provenance and evidence path
- [x] The illuminated path reaches every Root supporting the selection in one traversal
- [x] Contradicts relationships render as dashed mulberry paths, visually distinct from supporting paths
- [x] The reading panel opens the selected item's content as the illumination appears
- [x] Selecting a different item clears the previous illumination
- [x] Illumination is available to keyboard selection, not only pointer selection
- [x] The illuminated relationships are also conveyed to assistive technology, not by visual treatment alone

## Notes

**What was built.** `src/workspace/evidenceTrace.ts` is a new pure module, following `treeView.ts`'s seam: a breadth-first walk of the resolved graph, backward-only, through Supports and Answers (target back to source) and Derived From (source on to its Seed), reaching every Root and Seed upstream of the selection in one pass. Contradicts is walked separately, one hop only, since disagreement is a fact about the selection rather than a path to follow further. `GardenTree.tsx` renders the result: unrelated nodes and links soften via a `--dimmed` modifier class (opacity alone, the same carrier ticket 08 uses for Dormant), and every node's `aria-label` states outright whether it is "on the evidence path" or "contradicts the selection" — so the fact reaches assistive technology directly rather than through the visual treatment alone. Selection is already one code path for pointer and keyboard (ADR 0042), so illumination follows both without extra wiring, and the trace is derived from `selectedId` alone, so a new selection clears the old illumination for free.

**A real bug the browser check caught, twice.**
1. The first implementation traced evidence *undirected*: walking every Supports/Answers/Derived From edge both ways. In real Chromium, selecting a Claim also lit up an unrelated Harvest that happened to cite the same Root — sharing a citation is not evidence for either item. Fixed by making the walk backward-only (`backwardAdjacency`/`upstreamOf` in `evidenceTrace.ts`); locked in by the test "does not leak sideways through a Root shared with another supported item."
2. Code review (Standards and Spec axes, both `opus`, run against the commit that was `HEAD` before this ticket) independently caught a second bug from the same root cause of "test what a person perceives, not a proxy": `tracing` was derived as `trace !== NOTHING_TRACED`, which is true for *any* valid selection — so choosing a Branch, Root, or Seed with no evidentiary relationship of its own dimmed the entire Tree for no reason a person could see. A real-browser screenshot after selecting an unrelated Branch showed exactly this: the whole Tree faded to near-invisibility. Fixed by exporting `isTracing(trace)`, which checks whether the trace actually found anything (`evidencePathIds.size > 0 || contradictingIds.size > 0`), and re-verified live: selecting a Branch with no evidence now dims nothing (`0` dimmed nodes, screenshot-confirmed), while selecting a Claim still illuminates correctly.

**Other review findings fixed:** `dimmed` in `GardenTree.tsx` was re-deriving what `isLit` already computed, a second definition of "lit" that could silently drift — now reuses `isLit`. The Cross-link edge key (`${type}:${sourceId}->${targetId}`) was spelled independently in both `evidenceTrace.ts` and `GardenTree.tsx` — now exported once as `edgeKey` and imported. The `EvidenceTrace.supportingIds` field was renamed to `evidencePathIds` to match the vocabulary already used in the aria-label ("on the evidence path") and to stop implying it only carries the Supports relation when it also carries Derived From. CSS transitions lived only on the `--dimmed` modifier, so a node faded in but snapped back instantly when illumination cleared — moved onto the base `.garden-tree__node`, `.garden-tree__links path`, and `.garden-tree__cross-link` rules so both directions animate. Added a `:hover` restore for a dimmed node's opacity, matching the existing `:focus-visible` restore, so a pointer user has the same way to preview a softened node that a keyboard user already had. The BFS queue now uses a read cursor instead of `Array.shift()`, keeping the walk linear rather than quadratic, matching the anti-quadratic care already taken in `describeCrossLinksByItem` (ADR 0061).

**A deliberate scope decision, reviewed and kept as-is:** the ancestor (Parent) chain is not traced or kept lit. CONTEXT.md defines Parent as Tree placement, not provenance, and Supports/Answers/Derived From are the relationships CONTEXT.md actually names as carrying evidence and provenance. Both review passes judged this defensible. One consequence, also reviewed and accepted: a lit leaf's own hierarchical link to a dimmed ancestor Branch stays undimmed (a link softens only when *neither* endpoint is lit), so a glowing node never appears to hang disconnected from a faded one — this is deliberate, not an oversight.

**Verification.** `pnpm typecheck`, `npx vitest run` (962 tests, all passing, including 15 new pure-logic tests in `evidenceTrace.test.ts` and 15 new DOM/accessibility tests in `Workspace.test.tsx`), and `pnpm build` all pass. Real-browser verification was done twice against a `pnpm preview` build driven headlessly over CDP with a faked `window.showDirectoryPicker`: once against the initial (buggy, undirected) implementation, which is what surfaced bug 1 above via screenshot; once after both fixes, confirming — with screenshots — that selecting a Claim illuminates its Root and dims everything else including an unrelated Branch, that the Contradicts edge renders as a distinct dashed mulberry curve while non-illuminated Supports/Answers cross-links fade, that a two-hop chain (Root → Harvest → Question, reached only through the Harvest that answers the Question) lights up correctly from a single selection, that keyboard selection (Tab then Enter) produces the same illumination as a pointer click, and that `prefers-reduced-motion: reduce` collapses the new opacity transitions to `0.01ms` via the existing global rule from ticket 08 (no new motion-handling code was needed).

**Code review.** Two `opus` sub-agents reviewed the diff against the commit that was `HEAD` before this ticket (Standards axis and Spec axis, run twice due to a process error on the first pass — see the commit message). Both spec reviews independently verified all seven criteria as met, hand-traced the backward-only fix against the code, and confirmed no scope creep: only `evidenceTrace.ts`, `evidenceTrace.test.ts`, `GardenTree.tsx`, `Workspace.test.tsx`, and `app.css` were touched, `Workspace.tsx` was left untouched (ticket 11's sibling agent also changes that file), and the `app.css` changes are additive only (new rules, no edits to existing ones), to keep the two agents' work easy to merge.

**Scope not covered, deliberately:** a supporting Root that sits inside a currently-collapsed Branch, or outside a focused subtree (ticket 08's view state), will not visually render as lit until a person expands or unfocuses to reveal it — the trace itself still reaches it (verified independently of view state, since `traceEvidence` takes only the index and the selected id), but the drawing can only light what is currently on screen. This follows from ticket 08's collapse/focus being a deliberate, person-controlled narrowing of the view rather than something ticket 09 should override; auto-expanding the Tree to force a Root into view was judged out of scope for this ticket and is not built. The full Botanical Instrument visual system (ticket 10) was also not touched — illumination uses the existing opacity/colour tokens rather than any new visual treatment.
