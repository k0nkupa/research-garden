# 16: PWA offline application shell

**What to build:** A person who has loaded the application once can keep working on a permitted local folder without a network connection. The offline capability covers the application itself and nothing else — their Garden files and any tool results are never cached, so the offline shell cannot quietly become a second copy of their knowledge.

**Blocked by:** 06

**Status:** resolved

- [x] A service worker caches only versioned application assets
- [x] Garden files are never service-worker cached
- [x] Tool results are never service-worker cached
- [x] After an initial load, the human interface operates on a permitted local folder with no network connection
- [x] A new application version supersedes the cached shell rather than being shadowed by it
- [x] The web app manifest satisfies installability in the target browsers (ticket 01 shipped an SVG-only icon set; raster or maskable icons may be required)
- [x] Agent workflows are correctly reported as requiring their host connection when offline

## Notes

### What was built

- `src/entry/offline-shell/serviceWorkerCache.ts` — pure, fully unit-tested decision logic: `shellCacheName`/`staleCacheNames` for the versioned-cache lifecycle, and `shellCacheStrategyFor(url, origin)`, a **closed allowlist** returning `'network-first' | 'cache-first' | null` for exactly the document shell, `/manifest.webmanifest`, `/assets/*` (Vite's hashed build output), and the icon files — `null` for everything else, including cross-origin requests and the service worker's own script.
- `src/entry/offline-shell/serviceWorker.ts` — the service worker itself (install/activate/fetch). Both places that write to the cache — the runtime `fetch` handler *and* the install-time precache step — route every URL through `shellCacheStrategyFor`, so the allowlist genuinely governs everything written to the cache, not just the request path. Only `response.ok` results are ever cached, so a transient 4xx/5xx can never poison the offline shell. Marked `@ts-nocheck` with a comment explaining why (ServiceWorkerGlobalScope globals conflict with the app's DOM-lib tsconfig); every real decision lives in the tested module above, and this file's actual runtime behaviour was verified in a real browser (below), not assumed from the code compiling.
- `src/entry/offline-shell/registerServiceWorker.ts` — registers `/sw.js` on `window`'s `load` event, gated to production builds only (so the dev server is never intercepted), following the same environment-injection pattern `capabilities.ts` already uses so the guard logic is unit-testable without a real browser.
- `vite.config.ts` — a second Rollup entry point builds the service worker to a stable, unhashed `/sw.js`; a `precacheManifestPlugin` emits `dist/precache-manifest.json`, the exact list of that build's hashed asset filenames plus the document shell and the icons named in `public/manifest.webmanifest` (read from the manifest itself rather than a second hard-coded copy). `__SW_VERSION__` is defined from `Date.now()` at build time so the service worker's own script bytes differ on every production build.
- `src/capabilities/capabilities.ts` — extended the existing capability/readiness model (ticket 01's readiness gate) with a third, live signal: `online` (from `navigator.onLine`, re-read on `online`/`offline` window events). `AgentInterfaceStatus` is now `'available' | 'unsupported' | 'offline'` rather than a boolean, so the UI can distinguish "this browser will never have WebMCP" from "WebMCP is present but there is no connection right now" — the distinction ADR 0072 draws between the human interface (offline-tolerant) and browser-agent workflows (host-connection-dependent).
- `src/entry/ApplicationShell.tsx` — renders the corresponding notice, worded differently per reason (an `unsupported` browser is told plainly; `offline` is told the connection, not the browser, is the blocker, and that it will resume on its own).
- `public/icon-192.png`, `public/icon-512.png`, `public/icon-mask-512.png` — raster and maskable icons generated from the existing `icon.svg` via `rsvg-convert` (a one-time, local generation step — nothing added to the runtime or build dependency graph). `public/manifest.webmanifest` now lists all four icons (the original SVG plus these three), satisfying Chrome/Edge's installability requirement for 192×192 and 512×512 icons and a maskable icon.
- `src/entry/manifest.test.ts` — unit tests the manifest's structural requirements (name, standalone display, start_url, the required icon sizes, a maskable icon, and that every referenced icon file actually exists under `public/`).
- `src/entry/build-constraints.test.ts` — new `describe` block making the "by construction" claim (Garden files and WebMCP tool results are unreachable from the service worker) enforceable rather than only asserted in prose: every file under `src/entry/offline-shell/` is grepped for File System Access tokens and for `modelContext` (the WebMCP tool registry token `capabilities.ts` detects), and neither may appear anywhere. The offline-shell files were moved into their own `src/entry/offline-shell/` directory specifically so this check (and the equivalent Standards concern about a hand-maintained file list silently missing a future file) uses a directory prefix, matching the existing `src/filesystem/` idiom elsewhere in that same test file, rather than an enumerated list.

### How offline behaviour was actually verified (not just that the code exists)

Real-browser verification followed this repo's established convention (ADR 0064), using headless Chrome driven over the DevTools Protocol via `puppeteer-core` pointed at the system's installed Chrome, serving the real `pnpm build` output through `vite preview` — a throwaway verification harness in `/tmp`, not committed to the repo.

1. **First load, real precache.** Loaded the built app once online at a desktop viewport; polled until the service worker reached `activated`; inspected `caches.keys()` and each cache's entries. Confirmed exactly one versioned cache existed, containing the document, the manifest, all four icons, and every hashed JS/CSS/font file Vite emitted — proving the precache-manifest mechanism actually primes the *bundle*, not only the document (see the finding below this fixed).
2. **Offline boot.** Enabled CDP network emulation (`page.setOfflineMode(true)`) and reloaded. The app booted to the full ready state — "Create Garden" / "Open Garden" both present and interactive — with no network. Confirmed the offline emulation was real (not merely untested) by also fetching a deliberately uncached path and observing it fail with `net::ERR_INTERNET_DISCONNECTED`.
3. **Version supersession.** With the tab still open, ran a second `pnpm build` (producing a new `__SW_VERSION__` and therefore byte-different `sw.js`), forced `registration.update()`, and polled `caches.keys()` until it changed. Confirmed: the old versioned cache was deleted, exactly one new cache (under the new version's name) existed, and the active service worker's script URL reflected the update — `skipWaiting` + `clients.claim` + the versioned cache name working end-to-end, not just unit-tested in isolation.
4. **Manifest installability, Chrome's own verdict.** Queried `Page.getInstallabilityErrors` and `Page.getAppManifest` over CDP against the real running page: zero installability errors, zero manifest parse errors.
5. **Offline-vs-unsupported agent-status copy, in a real browser.** Real desktop Chrome has no `navigator.modelContext` at all (WebMCP is a ChatGPT-specific integration, not a standard Chrome API), so the `'unsupported'` branch was exercised natively by an ordinary headless Chrome load, and the `'offline'` branch was exercised by stubbing `navigator.modelContext` before navigation (simulating a browser that does have WebMCP) and then cutting the network. Confirmed the rendered notice said "You are offline…" and specifically did *not* say the browser "does not support WebMCP" — the two reasons render distinct, correct copy in a real browser, not only in the jsdom unit tests.

A real defect surfaced only by this process, not by any unit test: the very first version of `serviceWorker.ts` cached only `/` at install time (`cache.add('/')`), because a service worker does not control the page that is installing it — that page's own requests for its JS/CSS bundle never reach the *installing* worker's fetch handler. An offline reload after only one visit rendered the desktop-too-small screen correctly (viewport was the real bug there — headless Chrome's default 800×600 viewport, not an offline defect) once the viewport was fixed, but with the un-primed cache the bundle itself would have been unavailable on a genuinely fresh device. This is exactly why `vite.config.ts`'s `precacheManifestPlugin` and the manifest-driven install-time precache exist, and why this ticket's process explicitly distrusts "the code compiles" for the service worker.

### What the code review caught, and how it was resolved

Ran `/code-review`'s Standards and Spec axes (both on `model: opus`, as instructed) against `main`, comparing the uncommitted working-tree diff (nothing was committed yet at review time). Real defects found and fixed:

- **The install-time precache bypassed the allowlist.** `cache.add(url)` was called directly on every manifest entry without checking it against the cacheability predicate, so the "closed allowlist governs everything cached" claim was only true for the runtime fetch path. Fixed by routing every precache URL through the same `shellCacheStrategyFor` the fetch handler uses (see `serviceWorker.ts`).
- **Error responses could be cached.** Neither `networkFirst` nor `cacheFirst` checked `response.ok` before `cache.put`, so a transient 4xx/5xx could become the stored offline shell. Fixed with a shared `putIfOk` helper.
- **Duplicated document-routing logic.** `service-worker.ts` re-derived "is this the document" inline (`url.pathname === '/' || ...`) even though the same predicate already lived in `serviceWorkerCache.ts`, undermining the file's own claim that every decision is delegated to the tested module. Fixed by folding the strategy choice into `shellCacheStrategyFor` itself, which now returns which strategy applies (not just whether the URL is cacheable), so there is exactly one place that decision is made.
- **A hand-maintained file list in `build-constraints.test.ts` was a silent-gap ratchet risk** — a future offline-shell file could be added without anyone remembering to add it to the list, escaping the "never references Garden/WebMCP tokens" check. Fixed by moving the offline-shell files into `src/entry/offline-shell/` and switching the check to a directory prefix, mirroring the existing `src/filesystem/` idiom in the same test file.
- **Minor consistency nits, both fixed:** a nested ternary in `capabilities.ts` (the only one in `src/`) became two guard clauses in a named function; `ApplicationShell.tsx`'s inline `if`/`else` for the two unavailable-reason messages became a `Record`-keyed lookup, matching the existing `MISSING_CAPABILITY_HEADINGS` idiom exactly (and now fails to typecheck if a third reason is ever added without copy for it); the icon list that both `vite.config.ts`'s precache plugin and `public/manifest.webmanifest` needed is now read from the manifest by the plugin instead of duplicated.
- **Real-browser evidence for the `caches.match` offline fallback:** the review noted `caches.match(request)` without `{ ignoreSearch: true }` could miss the cached document on a navigation carrying a query string. Fixed for the document (`networkFirst`) path specifically, not the hashed-asset (`cacheFirst`) path, where an exact match is correct.

Findings triaged and **not** changed, with reasons:

- **A Spec-axis finding that going offline inside an already-open Garden shows no notice at all.** Checked `Workspace.tsx`'s own docstring, which states the Agent Access bar is ticket 17's responsibility, and confirmed by grep that no WebMCP tool registration exists anywhere in this codebase yet — only forward-looking comments citing tickets 17 and 18. There is currently no agent-facing affordance inside an open Garden to attach a status notice to; building one now would be pre-building ticket 17's UI, which is explicitly out of this ticket's scope per `Workspace.tsx`'s own comment ("the Agent Access bar (ticket 17) join this layout later"). The `agentInterface` signal this ticket adds to `resolveReadiness` is available for ticket 17 to consume once that surface exists.
- **`Date.now()` as the service-worker version, rather than a content hash of the build output.** A content hash would avoid an unnecessary cache invalidation on a byte-identical rebuild, but computing one requires patching an already-emitted Rollup chunk after all other asset hashes are finalized — meaningfully more build complexity for a non-functional benefit. `Date.now()` unconditionally satisfies the acceptance criterion ("a new version supersedes the cached shell"), which was verified end-to-end in a real browser.
- **`registerServiceWorker`'s injected-environment interface called "scope creep" for a ~10-line function.** This is the same environment-injection pattern `capabilities.ts` already documents as this codebase's established idiom for making browser-dependent decisions unit-testable without a real browser; it was modelled on that file deliberately, not added speculatively.
- **The `/^\/icon[-.]/` pattern in `shellCacheStrategyFor` admits any path shaped like an icon, not only the four that currently exist.** Left as a shape-based rule rather than an exact enumerated list: this app has no route capable of serving arbitrary content under that path prefix (Garden files are never served over HTTP at all), so the practical risk is nil, and an exact list would reintroduce the very duplication the manifest-driven precache list was built to remove.

### Deviations from a literal reading of the ticket

- The ticket's own acceptance criteria don't mention a manifest-driven precache list or a directory move; both were added specifically to close real gaps this ticket's own verification process (real-browser CDP checks, then code review) surfaced, not scope creep for its own sake.

### Criteria left unticked

None. All seven are ticked. Two are worth stating precisely rather than leaving as a bare checkmark:

- **"Tool results are never service-worker cached"** is enforced by a closed allowlist and an enforceable token-absence test, but is currently **vacuous** in the sense that no WebMCP tool call or tool-result flow exists anywhere in this codebase yet (confirmed by grep — only forward-looking comments citing tickets 17/18). The enforcement mechanism is real and will still hold once tool results exist; there is simply nothing yet that produces one to test against.
- **"After an initial load, the human interface operates on a permitted local folder with no network connection"** was verified for everything CDP automation can drive: a real build, a real offline network cut, and a fully booted, interactive ready state. It was **not** verified by actually completing a live `showDirectoryPicker()` folder selection while offline, because headless Chrome exposes no automation hook for that native OS dialog — a known limitation of browser automation tooling generally, not a gap specific to this implementation. This is backed by construction rather than by a click-through: the File System Access API is spec-defined as local/non-network, and `src/filesystem/`'s own layering tests (pre-existing, in `build-constraints.test.ts`) already establish that layer makes no network calls.
